# HANDOFF — автопостинг канала «25 лет стройки»

Последнее обновление: 2026-09-30.

## Как устроено

- Канал: https://t.me/stroyka_25let (публичный). Бот и канал задаются секретами репозитория `BOT_TOKEN`, `CHANNEL_ID`.
- Очередь: `queue/N.txt` — текст поста; `queue/media/N/*.jpg` — фото к нему (альбом, порядок по имени файла). Публикуется файл с наименьшим номером.
- Workflow: `.github/workflows/publish.yml`.
  - График: `0 14 * * 2,5` — вторник и пятница, 19:00 Екатеринбурга. Плюс контрольные запуски в тот же вечер `0 16` и `0 18` UTC (21:00 и 23:00 Екб).
  - **Защита от дублей:** публикация только если с начала текущего слота (последние вт/пт 14:00 UTC) в `main` нет коммита «Опубликовано: …». Поэтому запоздавшие, контрольные и ручные (Run workflow) запуски повторно не публикуют.
  - `concurrency: publish-queue` — запуски не идут параллельно; checkout берёт актуальный `main`.
  - Пост с фото: альбом `sendMediaGroup`. Если текст ≤ 1024 символов, он идёт подписью к первому фото; иначе после альбома отдельным `sendMessage`. После успешного альбома сразу коммит «Альбом отправлен: N.txt» (медиа удалены из очереди). Если текст не ушёл, повторный запуск отправит только текст.
  - После успеха: коммит «Опубликовано: N.txt», файл удалён из очереди.
- Ручной запуск: Actions → Publish scheduled post → Run workflow (ветка `main`). Безопасен в любой момент: если в текущем слоте уже была публикация, ничего не отправит.

## Инцидент 29.09.2026 — пропущен пост «Палладиум. Обрушение»

- **Что было:** GitHub запустил расписание 29.09 с опозданием почти на 5,5 ч (19:15 UTC = 00:15 30.09 Екб; запуски по cron у GitHub регулярно опаздывают на часы). Шаг публикации упал за 0 с: run `36617926787`, `curl` exit code 26. В Telegram ничего не ушло, частичной публикации не было.
- **Причина:** поддержка альбомов добавлена 25.09 в коммите `419ccb4` вместе с самим постом и до 29.09 ни разу не выполнялась. `chat_id` передавался через `curl -F chat_id=${CHANNEL_ID}`; значение вида `@имя_канала` curl трактует как «прочитать файл» и падает с кодом 26 ещё до сети (воспроизведено локально). Текстовые посты шли через `-d`, где `@` безопасен, поэтому раньше ошибка не проявлялась.
- **Исправление** (`2b2f7f6`): `--form-string` для `chat_id` и `media`; защита от дублей по слоту; `concurrency`; фиксация альбома отдельным коммитом; контрольные запуски. Основной график не менялся. Логика проверена локально на копии репозитория с тестовым двойником Telegram API: публикация, повторный запуск без дубля, повтор после сбоя текста без второго альбома.
- **Восстановление:** ручной запуск `36624902581` (workflow_dispatch на `2b2f7f6`), 29.09 20:14 UTC → коммиты `0eda0d2` «Альбом отправлен: 3.txt» и `5cd7365` «Опубликовано: 3.txt».
- **Проверено в самом канале** (t.me/s/stroyka_25let): альбом из 3 фото — пост https://t.me/stroyka_25let/19 (альбом занимает номера 19–21); текст — https://t.me/stroyka_25let/22, 1823 символа, совпадает с `queue/3.txt` (сравнение без учёта пробельных символов). Дублей нет.
